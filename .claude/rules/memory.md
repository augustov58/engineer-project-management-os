# Project memory, proposals, agent runs and the audit

Ground rules moved out of `AGENTS.md` on 2026-09-01, none rewritten. Claude Code loads this file when a
path in the frontmatter is read through the Read tool; from the shell, read it yourself. The rules that
apply to every path stay in `AGENTS.md`.

- A project's **memory** is `project_memory_versions` with **no identity table** — the project is the identity, since there is exactly one memory per job (ADR-0040). Nothing edits or deletes a version; the current memory is the latest, derived on every read. The size budget (4,000 characters) rides on every read and is **surfaced, never enforced**.
- A **proposal** is the approval request — the sketch's `approval_requests` table is refused. Its `base_content` is **snapshotted when the proposal is written**, so the diff under review cannot drift as memory moves; and the proposal is never edited — accept-with-edit writes the *version* from the engineer's text and keeps the agent's words on the proposal. The agent's one mutating tool writes proposals only; there is no accept tool, which is what "the agent never writes memory directly" is made of.
- Accepting a proposal whose `base_content` is no longer what the memory says is **refused**, never re-diffed (issue #42, recorded in ADR-0040). The snapshot stands: re-drawing the diff against today's memory would put text under review that the agent did not propose, and would leave an engineer's *edited* text — written line by line against the old base — meaning something nobody chose. The way on is reject and ask again. `stale` is derived on every read from the memory's current **content** against the base and stored nowhere, so a memory written back to what the base said is honest again; only a pending proposal is ever stale. The check runs inside the accept's transaction. The screen withholds Accept and says why, because a diff that misdescribes the commit it is offering is the defect, not the refusal.
- A proposal is answered **once**, and the database holds it (issue #42). Both routes settle the row by compare-and-set — the stamps in the `where`, the count checked — **first** in their transaction, so the audit row rolls back with the update it describes; a CHECK stands behind them. The pending read above each is not a bound: a concurrent accept and reject each passed it and each committed, leaving both stamps set, the wire reporting `accepted`, and an append-only audit carrying both answers. The accept route's `project_memory_versions.proposal_id` unique is untouched and still catches the race the version insert loses.
- `project_memory_versions.seq` is the **tie-break and nothing else** — never an identifier, never on the wire, not a count (issue #42). "The current memory is the latest" ordered on `created_at` then `id`, and `id` is a random v4 uuid while `created_at` is `TIMESTAMP(3)`, so two versions written in the same millisecond ordered by coin toss and the older could read as current. Which version is current is read in **one place**, `currentVersion` — the memory read, the proposal's base and the accept's staleness check all come through it, and `readMemory` counts rather than loading every version and taking its last, because a second way to work out which row is current is a second thing that can be wrong about it. The history's order is that one **reversed** and must stay its exact reverse; a test writes five versions in one millisecond and asserts both readings agree.
- An **agent run** is a row with the four stamps and no `kind` column, produces at most one proposal (`run_id` unique), and has **no retry route** — asking again is another row (ADR-0035's reason). The worker dispatches a third job name, `propose-memory-edit`, on the same queue.
- `AgentRunService` is the port ADR-0002 requires and **no Pi type appears outside `agent.ts`** — the SDK is imported lazily so a test process never loads it. The default refuses with "no model provider is configured"; `AGENT=pi` builds the real adapter. **`AGENT=pi` requires `AGENT_MODEL`**, `<provider>/<model>` (issue #157, ADR-0065), and the process refuses to start without it: every run is moved onto that model by `pinModel` once its session is built, and a model the deployment cannot find **fails the run** — never a fallback to whatever `findInitialModel` picked, which is how the machine ran a model nobody chose. It is set in `fly.toml`, where the next deploy reads it. **A provider error fails the run** (issue #162): `session.prompt` does not throw on one — the SDK appends an assistant message stopped on `error` and returns — so `failIfTheModelFailed` reads the **last** assistant message after every prompt and throws its sentence. **Unless the run's proposal already landed** — its own proposal tool answered 2xx by the route: the SDK calls the model again after every tool call, and an error on that wrap-up turn is not the run failing, the proposal being on the record. Without it every run type read *finished, proposed nothing*, and an extraction said *no correspondence here* about a document no model read. **Check a new model on the machine before naming it**: `alibaba-plan/deepseek-v4.1-flash` refused every call there (the `developer` role), and `qwen3.7-plus` answered without calling its tool, which loses the reply. The domain tools call the internal API over HTTP and never the database, are registered with **underscored names** (provider APIs reject the PRD's dotted spelling), and the session's tool list is an **allowlist** naming this product's domain tools and nothing else, so every built-in is absent rather than denied — the file tools `read`, `grep`, `find` and `ls` included. They were kept in slice 17 and described as scoped by `cwd`; the SDK's `resolvePath` uses `cwd` only as the base for a *relative* path, returns an absolute one as given and expands `~`, with no containment check in any of the four, so `cwd` never bounded them and a run could read the SDK's own credential store. A memory run reads no file, so they were removed rather than fenced (ADR-0041). Do not re-enable one without reading the vendor's resolver first.
- Every memory mutation writes an `audit_entries` row **in the same transaction**, and nothing updates or deletes one — append-only by construction. The audit was scoped to memory; **it no longer is** (story 106): every one of the sixty-two mutating routes writes a line, through the one leaf `apps/api/src/audit.ts`, and `POST /v1/projects/:id/memory/runs` — the memory mutation slice 17 itself left out — writes one too. The line is still written inside the mutation's own transaction and still takes its instant from the caller's `TimeSource`; what changed is only how many writers there are. `apps/api/test/audit.test.ts` reads the routes Fastify registered and fails if a mutating one is missing from its list, so the widening cannot silently un-widen.
- Since issue #111 (ADR-0055 part 2) every line also says **who** and **which row**. `actor_id` is read from the session the gate validated and **never from a request body** — `actorOf` in `gate.ts` is the one way one is built, and `routes/sessions.ts` is the one file that composes an actor itself, because signing in is the act of getting a session. It is null in **one route and three commands**: the ingest webhook, and `user create`, `user reset` and `user enable` on the machine. `agent_run_id` and `extraction_id` sit beside it under a CHECK that at most one is set — `sessions`' shape, because this product has two run records. `subject_type`/`subject_id` are **nullable in the database and required on `AuditLine`**: history genuinely has no subject and inventing one is a wrong answer, while `tsc` refuses a new writer that omits one. The subject is the row created or changed, and for a join the record the link was added to; it is **never a `sessions` row**, a session id being the credential. **No model carries a `created_by`** — a test reads `schema.prisma` with its prose stripped and says so.
- There are **75 writers in 18 files** as of issue #121 (72 before it, 69 at issue #112, 67 when #111 counted them, and the 61 in 15 the ticket and ADR-0055 say was already stale then). #121's three are the conversation opened on a project, the question typed into one, and the proposal the chat's run writes. Three writers are not on a route (`writeIssuance` serves two, and the two machine commands serve none), which is why `audit.test.ts` carries a **second sweep that reads the source** — `api.md`'s third sanctioned test exception, where the reason for it is written down. Do not narrow it to the route sweep: the route sweep cannot see those three, and it cannot see an `audit()` reached through a wrapper that supplies its own actor. **The count is kept here and nowhere else**: it was in that file's prose until #112 and came out rather than being bumped, which is ADR-0055 part 2's own note 4 applied to itself — a number repeated in comments and checked nowhere is how "three places and no more" was wrong six times. The sweep's own guard is a floor, not the count.
- A line's **prose reads in the project's zone** since issue #123 (ADR-0054 decision 3 as amended). Twelve of the seventy-five writers composed an instant into `detail` with `toISOString()`, and the feed renders `detail` verbatim beside a column already in the building's zone — so one row carried two faces of one event, which is #97's defect arriving through a stored string. They render through `zone.ts` now, **at the precision the value was typed at**: `readIn` where `apps/web`'s `composeInstant` types a day and a clock time and for a stamped instant, `dayIn` alone where `composeDay` types a day — a sign-off, a calculation, a held-since, and those three only. **No exception**: the report line names its walk to the minute although a walk is *filed* under its day (ADR-0030), because two walks on one building in one day would otherwise read as one sentence and `site visit recorded` names that walk to the minute anyway. Check which composer the screen uses before adding a thirteenth; printing a `00:00` nobody typed is the failure this rule exists against. The **zone is named once on the feed** and not per row (ADR-0059's rule for the report header), and `audit()` itself still never sees it — it is a leaf and the zone is the caller's, which is why nine Prisma selects widened and the archive route gained a read.
- **Every line written before 2026-09-21 keeps its UTC face**, and that is append-only working rather than a migration anybody forgot: 8 of the 35 lines on job 260113 still carry one, observed in a browser the day it changed. A feed read across that boundary shows both forms, which is ADR-0054's decision 4 — *a later frame defect is a dated correction, never a rewrite* — reaching the prose. The named trigger for reversing the whole answer is on the amendment: a project whose `timezone` turns out to be wrong leaves that prose wrong and unfixable, where the columns beside it are still recoverable.
- Both readers of the table go through **one `auditEntryOnTheWire` in `audit.ts`, beside the writer**. ADR-0048's "one record, two answers" is only true while the two hand back the same shape, and two `findMany` calls returning rows were one `select` away from disagreeing. The wire carries the actor by **name**, the run, and the subject — never the session.
- `GET /v1/projects/:id/memory/audit` has always returned the project's **whole** audit (`where: { projectId }`), which ADR-0044 recorded as a mismatch between the path and the answer. Since story 106 the answer is right and the path is the stale half. It is left where it is. The reason recorded here was that a screen links to it; **since issue #83 none does** — the project page's `The audit (N)` was what read it, and that block is gone, so `listMemoryAudit` is an exported reader with no caller. That weakens the reason without supplying a new one: renaming a route nobody asked to rename is still its own change, and the unbounded oldest-first answer is still the half of story 107's two questions the activity feed deliberately does not give.
- The feed **links a line to its subject** where `apps/web/app/subject-link.ts` has a screen keyed by that row's id, and renders plain text where it does not. The map is **deliberately partial on the screen's side**: a finding's URL carries its `number` and not its row id (ADR-0031), and a photograph, an observation and a document have no page at all. Do not put a number in `subject_id` to make one link — that is the interface's convenience in the record.
- The **activity feed is a read over `audit_entries` and never a second stream** (story 107, ADR-0048). `GET /v1/projects/:id/activity` returns the same rows the audit read returns, **newest first and bounded**; the audit read returns every line oldest first. That is what makes story 107's two questions two answers — the order and the bound, not the store. The PRD sketch's `activity_events` is refused: it would be a second place the same fact lives, with sixty-two writers of its own. Do not add one; the named trigger that would reverse it is the first time the feed must say something the audit must not.
- The `?limit=` **maximum of 200 is load-bearing**, not a page size. Without it the feed is the compliance record with a query parameter on it and the two questions collapse into one. The default is 50. The response is a **list whose length is not a count** — unlike exposure's and the clock's, it is bounded, so a screen must never render it as a figure (ADR-0016 keeps this product to two).
- `apps/api/src/routes/activity.ts` is named for the glossary's **Activity event** and `apps/api/src/audit.ts` for the table it writes: one is the reader, the other the writer, and ADR-0033's rule is that the route file matches its test file, which it does.
- `audit_entries` gets **no `seq`**, deliberately, where `project_memory_versions` has one (ADR-0048). Issue #42 added that column because *which version is current* is a value something computes; nothing computes a value from the audit's order, so two lines written in the same millisecond ordering by a random uuid is cosmetic. The trigger for adding one is anything deriving a value from that order — a "last thing that happened" on a screen would be one.
- The memory screen's stream carries both lists (`{runs, proposals}`) and `useLiveList` is generic over the payload since this slice; the `sseFrames` test helper moved into the harness when `memory.test.ts` became the second reader of a stream.
- **The agent is never given the ingest address.** `projectOnTheWire` carries it, and
  `projects_get` in `agent.ts` had handed the project read through verbatim — so the
  credential would have reached a model provider, the proposal and the audit. That tool now
  returns the three fields its description names. A test asserts it and fails without the
  projection. Anything else a project grows is covered by the same shape; do not go back to
  passing the response through.
